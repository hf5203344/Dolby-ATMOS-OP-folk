## 2. 审查方法 (采用方案 A: 问题驱动 + 横向一致性)

| 方案 | 描述 | 适合场景 | 选择理由 |
|------|------|----------|----------|
| **A. 问题驱动 + 横向一致性** (推荐) | 按模块逐一审查, 同时横向比对模块间接口, 按严重度分级 | 已有完整设计, 需找问题 | 既能深挖每个模块细节, 也能发现跨模块的不一致 |
| B. 质量属性模型 (ISO 25010) | 按 8 个质量属性逐项打分 | 大型组织内部审计 | 评分主观性强, 难以落地为具体改进项 |
| C. 对标参考模块 | 与 ViPER4Android、JamesDSP、官方 dolbycodec2hidl 对比 | 想要差异化定位 | 这些参考模块并不开源完整源码, 难以逐项对比 |

**审查视角 (4 个):**
1. **正确性** — 逻辑漏洞、配置错误、SELinux 路径错误
2. **一致性** — 跨模块 UUID/路径/常量是否唯一, 命名是否统一
3. **可测试性** — 测试用例是否真的能跑, 是否依赖真实设备
4. **可维护性** — 是否有单一事实源, 是否有版本管理, 是否有构建系统

**严重度分级:**

| 级别 | 含义 | 处置要求 |
|------|------|----------|
| **Critical** | 阻塞实现 / 设备会变砖 / 必定失败 | 必须在编码前修复 |
| **High** | 大概率导致功能失效 / 安全风险 / 数据丢失 | 应在 Phase 1 修复 |
| **Medium** | 影响可维护性 / 边界场景失效 | 应在 Phase 2 前修复 |
| **Low** | 文档/代码风格 / 性能优化 | 可延后处理 |
